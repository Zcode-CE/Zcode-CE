# 文案与格式纪律

> 面向 UI 文案、代码注释、跟踪文档三个「面」。三个面的**渲染器不同**，规则因此不同 —— 不要跨面套用。
> 每条规则的依据都指向实测或真实反馈，**不写凭空的洁癖**。

## 0. 唯一判据

用户原话（本文件的判据来源）：

> 「清理我们所有文件中『滥用』的 md 格式，比如 `**` 增大字号等。问题出于实际上大多数地方是没有必要强调的，
> 除非它『非常重要』以至于读者漏看会有真正的问题，但是很显然并没有，于是大量的本来是用来强调的增大字号符
> 最后给人的呈现就是『乱』和『吵』，让人不想看的同时遗漏掉被淹没的真正需要强调的事物。」

**判据（逐字采用，不重新论证）：**

> **删掉它，读者会不会少知道一件可操作、或需要知道的事？**
> 不会 → 删。会 → 留（并尽量缩短）。

**配套的第二问（防止「删了却把事实从界面上拿掉」）：**

> 如果这条信息屏幕上已经有了，**说清在哪里**（哪个元素/哪一行/哪个徽标），并让测试钉住那个替代载体。
> 只把断言的字面跟着文案一起放松，等于删掉了保证。

## 1. 为什么按「面」分：渲染器不同

| 面           | 渲染器                        | 实测事实                                                                                                                                                                              | 结论  |
| ------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| **UI 文案**  | **不保证支持 markdown**       | 两条路径并存：`SettingsRow` 的 description 是纯文本（`SettingsPageParts.tsx:142-144` `<div>{description}</div>`）；`ModelConfigHelp` 有 `emphasis()`（`ModelConfigHelp.tsx:102-113`） | 见 §2 |
| **代码注释** | **无产品渲染器**              | 全仓 `typedoc`/`api-extractor`/`jsdoc` **0 命中**；JSDoc 仅在 IDE hover 里渲染加粗（占注释 `**` 的 75%）                                                                              | 见 §3 |
| **跟踪文档** | **markdown（GitHub/编辑器）** | 确实渲染                                                                                                                                                                              | 见 §4 |

**这张表是全文的地基**：同一条 `**` 落在不同面上，一个是缺陷、一个是正常渲染。

## 2. UI 文案

### 2.1 规则：一律不用 markdown 强调

**规则**：UI 文案的取值里**不得出现 `**…**`**（也不得依赖反引号做行内代码）。

**理由**（不是「markdown 不好看」）：

1. **渲染器不保证支持**。同一份字典，一个键走 `emphasis()`、另一个键走纯文本 —— 实测已发生：
   `settings.remoteAssets.cdnBaseUrlDescription` 走纯文本，**字面星号直接上屏**（真浏览器实测 `hasLiteralStars=true`、`strongCount=0`，见 §2.4）。
   这是**缺陷**，不是风格问题。
2. **UI 的强调应由视觉语义承担**，不是字符：用 Tag / Badge / 标题层级 / 语义色。
   `DESIGN.md` 已有这条：正文与标题靠 `font-weight` + 语义色分层（`:230-232`）。

**确实需要强调时怎么办**（按优先级）：

- 首选**换成界面元素**（Tag/Badge/独立标题行）；
- 其次**用「」引出**（`用「」或直接陈述`）；
- 最后**重写句子**，让重要的事在句首或独立成句。

### 2.2 官方口吻是参考，不是模板

用户原话：

> 「Zcode 官方的 UI 文案已经很优秀了，我们没有必要搬其他项目的描述。但是问题是我们需要将模仿官方口吻与文案
> 作为参考与编写 UI 文案时的一个有意识的参考来做。」

⇒ **写 UI 文案时以官方源码为对照**（官方检出：`.reverse/91-upstream-checkout/zai-org-ZCode`，只读）。

**推论（重要）**：如果某条文案**本来就是官方的**（与官方逐字节相同），**不要改它** —— 动它等于偏离官方口吻。
实测本仓库 UI 字典里含 `**` 的 5 个键中，**4 个与官方逐字节相同**（`settings.modelProvider.help.*`），
它们走 `emphasis()` 渲染正确、加粗落在枚举项名上，**判定为保留**。

### 2.3 冗长解释性语句：四类必须删

判据同 §0。四类（来自真实反馈的归纳）：

| 类                   | 形态                                               | 为什么删                         | 正确形态                                     |
| -------------------- | -------------------------------------------------- | -------------------------------- | -------------------------------------------- |
| **解释设计意图**     | 「内置模型由应用内置配置提供，**因此**删除是隐藏」 | 讲我们怎么想的，不是用户要做的事 | 删；只留事实                                 |
| **复述屏幕已有信息** | 说明里再把上方字段已经说过的边界念一遍             | 同一事实在屏幕上出现两次         | 删（**并证明替代载体还在**）                 |
| **自夸**             | 「如实标注」「绝不静默」                           | 做到了自然看得见                 | 删                                           |
| **指路式引导**       | 「修改请到「X」子页」                              | 目标入口就在屏幕上，用户点得过去 | 删（前提：**入口可见且可点**，并用测试钉住） |

**「出路」与「指路」的分界**（这条最容易判错）：

- **出路 = 可执行信息**：具体命令、参数、文件名、下一步动作（如「重试；仍失败时重启 ZCode」）→ **保留**；
- **指路 = 导航**：「去另一个页面」→ **删**，因为导航本来就摆在界面上。

**⚠️ 明确不在删除范围**（删了就违反「如实声明」纪律）：

- **失败分支的可操作说明**（每个失败码给用户能做什么）；
- **常驻安全提示**（暴露范围、令牌等同 agent 级访问、链接即凭据）；
- **首次危险动作前的确认**；
- **升级带来的行为变更告知**；
- **「未验证」的如实标注**（不得写成「已验证」，也不得因为「读起来啰嗦」而删）；
- **否定式采集声明**（「不采集 X/Y/Z」）。

这些在 `.reverse/90-upstream-v3143/VOICE-DRIFT.md` §5 被列为「我们比官方更清楚的地方」（12 处，6 处有测试护栏），
**清理时不得顺手抹掉**。

### 2.4 验收方式：必须跑真实渲染

**改 UI 文案后不得只改字符串就宣称修好** —— 必须证明**用户实际看到什么**。

本仓库的现成做法：**临时渲染壳 + 真浏览器**（参考 `.reverse/90-upstream-v3143/remote-tabs-harness/`）。
渲染壳的要点：

1. 渲染**产品组件本身**（不是复制一份 DOM）；
2. 用**真实 i18n 字典**与**真实 Tailwind 样式**；
3. 读 `innerText`（用户看到的那一行），不读源码字符串。

本任务的可复跑样例：`.reverse/92-copy-format/harness/`（`vite build` + `node probe-render.mjs`）。

**判据要钉在「用户看到的那一行」上**：源码扫描只能证明「字面量里有 `**`」，
不能证明「屏幕上出现了星号」—— 后者才是缺陷。

## 3. 代码注释

### 3.1 规则：不用 `**` 强调

**规则**：`//`、`/* */`、`/** */` 的**注释正文**里**不得**用 `**…**` 做强调。

**理由（已修正，见下）**：注释不承载**稳定的**强调语义 ——

1. 本仓库**没有配置任何文档生成器**（`typedoc`/`api-extractor`/`jsdoc` 在根与各包 `package.json` **0 命中**），注释不会被渲染成文档页；
2. JSDoc 只在 **IDE hover** 里渲染加粗，那是开发者工具、不是产品面；
3. 真正的伤害是**一致性**：同一份注释里有的地方加粗、有的不加，读者**无法从中读出「哪里真的重要」**，
   于是既「乱」又「吵」—— 这正是用户描述的现象。

> **口径修正记录（task-94）**：本规则最初的理由写成「无渲染器 ⇒ 读者看到字面星号」。
> 实测后**该表述对 `//` 与普通块成立、对 JSDoc 不成立**（IDE hover 会渲染）。
> 结论不变，但**理由改为上面三条**，以免后人用「可是 IDE 里能加粗」推翻整条规则。

### 3.2 三类形态的处理

| 形态                                        | 例子                                                    | 处理                                                  |
| ------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| **A · 否定词**（`不是`/`不`/`不得`/`唯一`） | `**不是** OAuthClientProvider`、`故意**不在此声明**`    | **多数保留**（漏看会理解反）—— 但改成直接陈述，不加粗 |
| **B · 数量/范围**                           | `**丢弃整个 server**`、`只作为**本 caller 的等待预算**` | **去 `**`\*\*（读者不需要被提醒「全部」就是全部）     |
| **C · 既有事实**                            | `**逐字一致**`、`共用的唯一真相源`                      | **去 `**`\*\*（是断言不是警告）                       |

### 3.3 ⚠️ 不是强调的 `**` —— 护栏必须排除

机械规则「注释里不得出现 `**`」会**误杀**下面三类（它们是真语法）：

| 形态                            | 位置                                                  | 真身                       |
| ------------------------------- | ----------------------------------------------------- | -------------------------- |
| `**` glob 通配符                | `packages/services/src/file/workspaceFileIgnore.ts:7` | gitignore 语法             |
| `**:[[…]]` Tailwind v4 后代变体 | `packages/ui/src/components/ui/command.tsx:121`       | 样式类名                   |
| `"**"` 解析器分隔符             | `ModelConfigHelp.tsx:104`                             | `emphasis()` 的 split 模式 |

⇒ **护栏按「注释内的成对强调」判**（`\*\*[^*\n]+\*\*`），并排除 glob / Tailwind 变体上下文。
不要用「出现 `**` 即失败」这种过钝的形态规则。

### 3.4 规模与口径（实测）

`**` 在**注释正文**里共 **5432 处**（590 个文件，`git ls-files` 口径）：

| 包                  | `**` 数 | 文件数 |
| ------------------- | ------- | ------ |
| `apps/zcode-cli`    | 2586    | 261    |
| `packages/ui`       | 1249    | 188    |
| `packages/shared`   | 514     | 43     |
| `packages/server`   | 465     | 24     |
| `packages/desktop`  | 375     | 34     |
| `packages/services` | 131     | 22     |

按注释种类：`/**` JSDoc **4081**（75%）、`//` **1315**（24%）、`/*` 普通块 **36**（1%）。

> ⚠️ **统计口径**：必须用 `git ls-files`。扫全目录会得到 **82798**（**15 倍虚高**），
> 因为 `packages/desktop/mock-cdn/`、`bundled-agents/`、`out/`、`dist-release/` 是**生成物与载荷**。

量大且机械 ⇒ **先做一个包做样板，把脚本与判据给 Lead 复核，再铺开**。
不要一次改几千个文件（无法复核）。

## 4. 跟踪文档

### 4.1 规则：允许，但有纪律

markdown 在 `docs/`、`README*.md`、`AGENTS.md` 里**确实按 markdown 渲染** ⇒ 问题不是「非法」，而是
**滥用导致没有重点**（用户原话：「乱」和「吵」）。

**「滥用」的可判定定义**（三个条件同时成立）：

1. 落在**散文行**上 —— 表格行里的 `**` 是「列名/值」的结构标注，**不是强调，先排除**
   （实测：表格占全部 `**` 的 **19.3%**）；
2. 同一个 `##` 小节内散文 `**` 对数 **> 5**；
3. 逐个按 §0 判据检查，**多数可删**。

**阈值 5 从语料来（不是凭空定）**：实测 363 个含散文强调的小节 —— p50=4、p75=8、p90=17、p95=26、max=48；
**62% 的小节 ≤5 对**，46% ≤3 对。取 5 = **多数派的上界**。

### 4.2 允许保留的 `**`（白名单，不按数量判）

- **表格表头/关键值**（结构标注，不是强调）；
- **危险/不可逆操作的警告**（漏看会真的出问题）；
- **「不要做 X」的否定式**（漏看会做错）；
- **与官方/上游的差异标注**（漏看会误以为一致）。

### 4.3 与 `release-notes.md` 的关系

`release-notes.md` 的**口吻与结构**由 `docs/operations/release.md` 管（面向用户、不写内部语汇）；
**本文件只管它的 markdown 强调纪律**。两份文件**不重复规定**，各管一段。

可机械判定的部分加测试，**带正反例**，并做**变异验证**（改坏 ⇒ 变红）。
实现见 `packages/ui/test/copyFormatGuard.test.ts`。

### 6.3 两个真实踩过的坑（写下来，避免重犯）

**坑 1 · 只查 `git ls-files` 会漏掉「刚写的新文件」。**
变异验证实测：在**未跟踪**的新文件里写 `**`，护栏**不报**（`ls-files` 看不到它）。
而那恰恰是最可能出现新注释的地方。⇒ 改为 `ls-files` + `ls-files --others --exclude-standard`，
并**让基线生成器用同一套文件集**（否则基线与护栏口径不一致，会互相打架）。
生成物目录都已在 `.gitignore`（`git check-ignore` 实测命中 `out/`、`dist/`、`mock-cdn/`），所以带上未跟踪文件不会把生成物算进来。

**坑 2 · 变异验证的「还原」必须用变异前那一刻的备份，且还原后要重新核对 diff。**
本轮真实事故：还原 `zh-CN.ts` 时用了一个**更早**的备份，静默吞掉了同一文件上**后来**的改动（测试全绿，diff 却少了内容 —— 只看测试会漏掉）。
⇒ 规矩：**每次变异前现取备份**；还原后**除跑测试外，还要 `git diff` 核对改动集是否与变异前一致**。

### 6.4 清理的顺序与边界

- **按面分批**，每批一个可复核的完整单元：UI 文案（P0）→ UI 冗长句 → 注释样板（1 个包）→ 铺开；
- **注释面用棘轮**：不可能一次清完 2619 对，但**不许新增**；清理后用 `gen-copy-baseline.cjs --write` 收紧基线，进度单向推进；
- **不许用 `git checkout` 还原自己的工作** —— 本轮实测它会把同文件上其它改动一起丢掉（见坑 2 的同族）。

## 7. 棘轮基线：生成方式与口径（后人复算用）

基线文件 `.copy-format-baseline.json` 由
`node .reverse/92-copy-format/tools/gen-copy-baseline.cjs --write` 生成，
由 `packages/ui/test/copyFormatGuard.test.ts` 读取。**两者必须用同一套口径**，否则会互相打架。

### 7.1 口径（四条，缺一条数字就对不上）

1. **只统计 git 能看到的文件**：`git ls-files packages apps`
   **加上** `git ls-files --others --exclude-standard packages apps`。
   - **为什么必须带未跟踪文件**：只查 `ls-files` 会漏掉「刚写的新文件」—— 而那恰恰是最可能出现新注释的地方。
     变异验证实测：在未跟踪的新文件里写 `**`，护栏**不报**（已修）。
   - **为什么不能扫全目录**：`packages/desktop/mock-cdn|bundled-agents|out|dist-release` 是生成物与载荷，
     扫进去会让注释强调数从 **2619 虚高到 82798（15 倍）**。
     生成物目录都已在 `.gitignore`（`git check-ignore` 实测命中 `out/`、`dist/`、`mock-cdn/`），
     所以 `--exclude-standard` 不会把它们带进来。
2. **只统计注释正文**：用 TypeScript scanner 取注释 token，剥掉 `/**`、`/*`、`//` 定界符与 `*/`。
   - **为什么**：字符串/模板里的 `**` 是**产品输出**（见 §7.3），不是注释。
3. **只统计成对强调**：`\*\*[^*\n]+\*\*`，并**排除非强调形态**（glob `**/`、Tailwind 变体 `**:[[…]]`）——
   按「紧邻字符」判，不用宽泛字符类（那会误杀真强调）。
4. **文件集与判据都要与护栏一致**：基线生成器与护栏各写一份口径迟早会漂移，改一处必须改两处。

### 7.2 自洽约束（护栏会断言，防手改）

- `total` **必须等于**各文件计数之和（手改单个数字会立刻被抓）；
- 基线里**不得包含已不存在的文件**（文件删/改名后必须重新生成）；
- **不许手工把基线数字改大**来让护栏变绿 —— 那正是棘轮要防的事；
  只有**既有注释被清理、数字下降**时才用 `--write` **收紧**基线。

### 7.3 ⚠️ 注释口径的边界：产品输出里的 markdown 是**合法**的

**这一条是本判据存在的理由，务必先读。**

同一个文件里，`**` 可能有两类完全不同的用途：

| 类别                        | 例子                                                            | 该不该清                       |
| --------------------------- | --------------------------------------------------------------- | ------------------------------ |
| **注释正文**                | `// 本仓库**不随包分发**该 SDK`                                 | **要清**（棘轮管的就是这一类） |
| **产品输出（字符串/模板）** | 飞书卡片消息：`{ tag: "markdown", content: \`**\${title}**\` }` | **绝对不清**                   |

**真实实例**（`packages/services/src/bots/providers/feishuProvider.ts`）：该文件里
**模板字符串中 4 处** `**` 是**发给飞书的卡片 markdown**（飞书的渲染器**支持** markdown，加粗是**预期效果**），
**注释中 2 处**才是要清的。若判据写成「全文数 `**`」或「注释与代码一起清」，**会把飞书卡片的加粗弄坏**。

⇒ **通用规则**：清理前先问「这段 `**` 最终会交给谁渲染」。

- 交给**支持 markdown 的渲染器**（飞书卡片、GitHub、发布说明）⇒ **合法**，不动；
- 交给**纯文本渲染器**（UI 的 `SettingsRow` description）⇒ **缺陷**，必须删（§2）；
- **没有渲染器**（代码注释）⇒ **噪声**，按 §3 清。

**同一个字符，三种判定 —— 判据是「谁渲染它」，不是「它长什么样」。**

## 8. 过程纪律（本轮真实事故提炼）

这三条都来自本轮**实际发生**的事故，不是假想：

1. **「只删标记」必须逐份证明，不能只跑一份就推广。**
   证明方式：把改前（`git show HEAD:<file>`）与改后**各自去掉 `**`** 再逐字节比对。
本轮两次踩到「删标记时带走了紧邻的一个双空格」（`。 因此`→`。因此`），**都是靠这条比对抓出来的** ——
   只看「测试是否变绿」不会发现（它根本不影响渲染）。

2. **变异验证的「还原」必须用变异前那一刻的备份，且还原后重新核对 diff。**
   本轮真实事故：还原 `zh-CN.ts` 时用了**更早**的备份，静默吞掉同一文件上**后来**的改动 ——
   **测试全绿，diff 却少了内容**。同理：**不要用 `git checkout` 还原自己的工作**（它会连带丢掉同文件的其它改动）。

3. **证明方式本身也是一种约束。**
   本轮实例：某处表格里的加粗本可删，但格式器会要求**重排整张表的对齐** ⇒ 破坏「逐字节相同」的证明 ⇒ **主动撤回那处**。
   **不要为了多清一处而牺牲证据链。**

## 9. ⚠️ 本轮最重要的一个发现：护栏曾经「绿着但没在守」

**这一节必须读。** 它记录的是一个**假阴性**缺陷 —— 护栏一直是绿的，但它**漏掉了 21% 的目标**。

### 9.1 缺陷本体

注释提取器最初用 `ts.createScanner(...)` 的裸 `scan()` 循环取注释。**它在遇到模板表达式之后会失去同步**：

```ts
const greeting = \`hello \${name} world\`;

// 模板之后的注释：这一段必须被抓到
export const probe = 1;
```

实测（`tools/prove-extractor-fix.cjs` 可复跑）：

- **裸 `scanner.scan()` 数出 0**（漏）；
- **涂白 + 逐字符扫描数出 1**（正确）。

全仓口径：裸 scanner 报 **2627**，正确实现报 **3332+** ⇒ **漏约 705 对（21%）**。

**为什么这比"多报"严重得多**：多报会立刻变红、被人修掉；**漏报是绿着但没在守** ——
新写的强调会被静默放过，而护栏的全部价值就是拦住它。

### 9.2 同族的第二个缺陷

用正则 `/\/\*[\s\S]*?\*\//` 找块注释也不可行：行注释里出现含 `/*` 的文本时
（真实案例 `// postgres://admin:secret@host → postgres://***REDACTED***@host`），
正则把它当成块注释起点，**一路吃到几百行之后的某个 `*/`** ⇒ 整段被静默跳过。

⇒ **正确做法（两条一起用）**：

1. 用 AST 把**字符串/模板/正则/JSX 文本涂白**，只留注释与代码骨架（注释边界因此没有歧义）；
2. **逐字符扫描** `/*` 与 `//` 定界符，**不要用正则**。

### 9.3 顺带发现的第三类：脱敏占位符

`***REDACTED***` 里含 `**REDACTED**`，两侧是星号 ⇒ **不是 markdown 强调**。
按紧邻字符判可排除：`before === "*" || after === "*"`。
（另两类同族：glob 的 `**/`、Tailwind 的 `**:[[…]]`。）

### 9.4 教训（写给后人）

1. **"护栏是绿的"不等于"护栏在守"** —— 必须用**变异验证**证明它会红；
   本轮正是靠"在模板之后写一个 `**`"这条变异，才发现旧实现根本不看那段。
2. **同一份判据有两处实现时，必须交叉验证**（护栏与基线生成器）。
   本轮还额外写了**第三种独立实现**（手写状态机）来裁定谁对 ——
   **两种实现不一致时，不要挑一个"看起来对"的，要独立裁定。**
3. **验证"代码未变"时不要用被测对象自己的解析器**。
   本轮真实事故：我用**同一个有 bug 的裸 scanner** 去证明"只改了注释、代码没变"，得到**误报**（说代码变了）。
   换成 `ts.transpileModule(..., { removeComments: true })` 后确认**逐字节相同**。
   ⇒ **验证工具与生产工具不能是同一个（可能有同一个盲点）。**

### 9.5 口径订正记录

因上述修复，注释强调的**全仓总数由 2627 订正为 3372**（635 文件）。
**这不是"基线被写松"，恰恰相反**：是修掉假阴性后**第一次看到真实值**。
判据：修正后的实现通过了 **5 个人工逐行核对的样例**（`tools/verify-extractor-fixtures.cjs`，exit 0）：
`file-config.adapter.ts`=1、`model-catalog-port.ts`=9、`session-facade.ts`=2、`child-source.ts`=14、`exportLogs.ts`=0。

**为什么用「人工核对样例」而不是「再写一个独立实现做交叉验证」** —— 这是本轮最值得记住的教训之一：
我先写了两版"独立实现"，**两版都是验证工具自己错**：

- 手写状态机处理不好**跨行模板** ⇒ 卡在模板态，把之后所有注释漏掉（某文件报 0，人工核对真值 2）；
- AST `leading/trailing comment ranges` 会漏掉部分注释（某文件报 8，人工核对真值 9）。

⇒ **两种实现不一致时，不要挑一个"看起来对"的** —— 去**人工核对少量样例**，并把它固化成断言。
「再写一个实现」并不自动等于「独立验证」：它可能带着同一类盲点，也可能自己引入新盲点。

## 10. 判据本身也要被验证（覆盖率）

**新增的团队规矩**（本轮从一次真实事故提炼）：

> **一条一直绿的护栏，不能据此认为它在守。**
> 必须能回答「**它数的是不是全量**」—— 即**先证明判据的覆盖率**，再谈它拦住了什么。

这条是「护栏只有真拦过一次才算被证明有效」的**对偶面**，两者都成立：

- 前者防「**它从没拦住过任何东西**」；
- 后者防「**它拦不住，但看起来在拦**」。

### 10.1 本轮的实例

注释提取器用裸 `ts.createScanner().scan()` 取注释，遇**模板表达式**后失同步，
之后的注释全部读不到 ⇒ **漏 725 对 / 21.5%**（2647 vs 3372）。
护栏**一直绿**，但五分之一的注释在它视野之外。完整复盘见
[`.reverse/92-copy-format/EXTRACTOR-FALSE-NEGATIVE.md`](../../.reverse/92-copy-format/EXTRACTOR-FALSE-NEGATIVE.md)。

**验证覆盖率的方法**（本轮采用）：

1. **人工逐行核对少量样例**，把它固化成断言（`tools/verify-extractor-fixtures.cjs`）；
2. 特意挑**考边界**的样例：含 `/**` 开头符的、含跨行模板的、含脱敏占位符的。

### 10.2 ⚠️ 「写两个实现互相验证」是最容易骗过自己的形式

本轮真实教训：我为提取器写了两版"独立实现"做交叉验证，**两版都错**：

- 手写状态机处理不好**跨行模板** ⇒ 卡在模板态，之后注释全漏（某文件报 0，真值 2）；
- AST `leading/trailing comment ranges` 会漏注释（某文件报 8，真值 9）。

**为什么**：两个实现往往**出自同一个错误理解**，于是带着同一个盲点，交叉验证给出**虚假的安心**。

⇒ **两种实现不一致时，不要挑一个"看起来对"的 —— 去人工核对少量样例。**
「再写一个实现」不自动等于「独立验证」。

### 10.3 判据工具本身是嫌疑对象时，要换不同来源的工具

本轮实例：我用**同一个有 bug 的裸 scanner** 去证明"清理只改了注释、代码没变"，得到**误报**；
换 `ts.transpileModule(source, { removeComments: true })` 比对后确认**逐字节相同**。

⇒ 用被测对象自己的解析器去验证它，等于**让嫌疑人给自己作证**。

## 11. 11 条护栏各自守什么、不守什么

**覆盖对象必须写清** —— 否则后人会把"某条护栏绿了"误读成"这一类问题都安全了"。

| #   | 护栏                                               | **守**                                                                   | **不守**                                                        |
| --- | -------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------- |
| 1   | `[zh-CN]` UI 取值不得含强调                        | `zh-CN.ts` 的**字符串取值**                                              | 注释；其他语言文件；运行时拼出来的字符串                        |
| 2   | `[zh-CN]` 例外清单的键必须存在                     | 例外不会静默失效                                                         | 例外本身是否**该**存在（那是人工判断）                          |
| 3   | `[en-US]` UI 取值不得含强调                        | 同 1，英文侧                                                             | 同 1                                                            |
| 4   | `[en-US]` 例外清单的键必须存在                     | 同 2                                                                     | 同 2                                                            |
| 5   | 判据自检（正反例）                                 | 正则会认强调、不误杀 glob/Tailwind                                       | 判据的**覆盖率**（见 §10）                                      |
| 6   | 提取器自检（取值 vs 注释）                         | 提取器不会把注释当取值                                                   | 取值的完整性（漏掉的取值它不知道）                              |
| 7   | **注释棘轮**（不得超过基线）                       | `packages/**` `apps/**` 里**git 可见**文件的**注释正文**成对强调数不增长 | 文档（`docs/**`）；代码字符串里的 `**`（那是产品输出，见 §7.3） |
| 8   | 基线自身一致（total == 各文件之和、无已删文件）    | 基线不会被手工改松                                                       | 基线数字是否**真实**（要靠 §10 的覆盖率验证）                   |
| 9   | 注释判据自检（glob/Tailwind）                      | 不误杀 glob 与 Tailwind 变体                                             | 脱敏占位符（由第 10 条守）                                      |
| 10  | **假阴性回归**：模板之后的注释必须被读到           | 提取器不会退回裸 scanner 的写法                                          | 其他未想到的失同步形态                                          |
| 11  | **假阴性回归**：行注释里的 `/*` 不得被当块注释起点 | 块注释边界不会被行注释内容污染                                           | 其他未想到的定界符歧义                                          |

**明确不在护栏覆盖内**（需要人工把关）：

- **文档**（`docs/**`、`README*.md`、`AGENTS.md`）—— 数量大、形态多，靠人工按 §4 判；
- **UI 文案是否"冗长/解释性"** —— §2.3 的四类是判断，不是机械判据；
- **代码字符串里的 `**`** —— 飞书卡片这类**支持 markdown 的产品输出\*\*是合法的，清了反而坏（§7.3）；
- **例外清单的取舍** —— 第 2/4 条只保证例外"不会静默失效"，不保证它"正确"。
