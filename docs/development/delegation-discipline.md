# 派单纪律（Delegation Discipline）

> **用途**：把并行委派（agent team / subagent）的**踩过的坑**固化成可执行规则，避免同一类事故重演。
> **不是**流程介绍 —— 工具怎么用看宿主文档；这里只记**我们付过代价的教训**。
> **建立原因**：2026-09-25 排查 smoke flaky 时，**多位成员各自解包分发包副本**（每份 tarball 78 MB → 解包约 400 MB）到 `/tmp`，
> 累积把主机磁盘写满（`ENOSPC`）。后果不是"慢一点"，而是**整个会话失去执行能力**：`run_code` 的 worker 需要先写临时文件才能启动，
> 磁盘满 ⇒ **连 `return 1` 都跑不了**，累计 480+ 次尝试全部失败，且**无法调用任何工具报告阻塞**（所有工具都经由那个 worker）。

## 一、派单前必须写进任务的三项

| 项                         | 为什么                                           | 写法示例                                                                 |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------ |
| **磁盘预算**               | 这次事故的直接原因                               | 「产物副本解包到 `/tmp/<专用名>`；**总占用不超过 1 GB**；用完 `rm -rf`」 |
| **临时产物用后即清**       | 成员结束时不清理，占用会累积到下一个成员         | 「结束前删掉你创建的临时目录，并在回传里写你删了什么」                   |
| **优先复用同一份解包产物** | N 个成员各解一份 = N × 400 MB；共享一份 = 400 MB | 「解包产物已在 `/tmp/zcode-artifact`（只读复用）；**不要另解一份**」     |

**判据**：任务描述里**没有**这三项 ⇒ **这份派单不合格**。

## 二、共享工作区的写范围纪律

- **写范围必须互斥**（`write_scopes` 只是建议，不是锁）—— 两个成员改同一个文件，后写者会覆盖前写者且**不会有任何报错**。
- **不要派两个人做同一件事**：本次 `smoke-flaky-fix` 与 `smoke-timing-fix` 被派了重叠的排查目标，
  结果**两人各自解包、各自探针、各自得结论**，磁盘翻倍、结论还互相矛盾。
  **正确做法**：先派一个查根因，**拿到结论后再派**实现/验证。
- **派单要写清"不许改什么"**：本次有成员在任务范围外改了仓库文件（虽然后来自行发现并回退）。

## 三、成员回传必须包含的字段

| 字段                        | 为什么                                                                                             |
| --------------------------- | -------------------------------------------------------------------------------------------------- |
| **门禁的真实结果**          | 「没跑」与「通过」是两回事 —— 本次有成员明确写「**全部未跑**（不是通过，是未执行）」，这是正确做法 |
| **改了哪些文件**            | 便于 Lead 核对写范围；本次有成员写「`scripts/` 相对 HEAD 零改动」——**可核对**，很好                |
| **推翻/证实了哪些既有结论** | 本次最有价值的回传是**推翻 Lead 的归因**并给出判别实验                                             |
| **未验证项与卡点**          | 磁盘满时成员的「我无法启动、需要清理 X」是有用信息                                                 |

## 四、Lead 侧的义务

1. **派单前先自己查一遍根因** —— 把「已确认」与「待验证假设」分开交给成员。本次 Lead 连续给了两个**被推翻**的归因，
   成员为此浪费了探针时间。**判据**：派单里出现"我猜/可能是"时，要么标成**待验证假设**，要么先自己验。
2. **归因必须用判别实验**，不是机制推理 —— 本次组员做了 Lead 没想到的实验（把打包产物里 `onExit(130)` 改成 `131`，
   看结论是否跟着变 ⇒ **8/8 全变**）才定位到真实触发者。**只靠"读代码推理机制"给出的归因，本批被推翻了两次。**
3. **判据工具本身是嫌疑对象** —— 本次 Lead 在**剥 ANSI 的原始字节流**上做正则，而 ANSI 是**差分渲染**
   （旧内容不重发也不删除）⇒「流里出现过 X」**不等于**「屏幕上现在有 X」。成员改用**真终端模拟器**才看到真相。
   **凡是要读"屏幕/渲染结果"的判据，必须用终端模拟器，不能对原始字节流做正则。**
4. **不要用 `continue-on-error`（或任何等价物）吞失败** —— 见下节。
5. **并行期间禁止用 `git checkout` 批量回退文件** —— 见 §4.1（2026-09-27 事故）。

### 4.1 并行期间禁止批量回退（2026-09-27 实测事故）

**事实**：Lead 发现自己先前的注释清理工具**越界修改了 4 个历史基线文件**，于是执行

```bash
git checkout -- packages/ui/src/remoteControlPanelModel.ts packages/ui/src/RemoteControlPanel.tsx \
                packages/ui/src/RemoteControlImBotTab.tsx packages/ui/test/remoteControlPanel.test.ts
```

**后果**：这 4 个文件里，有**一个成员（Task F3）已经落盘的功能实现**（IM 机器人 tab 不渲染，
含其新增的 `canRenderRemoteControlImBotTab` 与两条测试断言）。整块 checkout 把它一起还原到 HEAD，
成员的功能改动**静默消失**。成员靠 mtime（同秒批量写）+ 内容对比 + 「其余 6 个文件未被还原」
自己定位并上报，Lead 才意识到是自己所为。

**为什么容易踩**：Lead 的回退意图是「撤销我自己的越界清理」，但 `git checkout <file>` 的作用域是
**整个文件**，不是「我改的那部分」。在多成员并行、同一文件被多人先后写入时，
整块回退 = **连带撤销他人的工作**。

**规则**：

1. **并行期间不得用 `git checkout -- <file>` / `git restore <file>` 回退文件**。
   要撤销自己的改动时：① 用**精确 edit** 反向改回；② 或先 `git diff <file>` 确认该文件当前
   **只含自己的改动**；③ 或先与正在该文件上工作的成员确认。
2. **回退前必须查该文件是否有人正在改**：`git status` 只能看到「有改动」，
   看不到「谁在改」——因此**并行期间默认假设有人在改**，走上面的 ①。
3. **成员应能自证**：本事故中成员能快速定位，靠的是「记下自己文件的 mtime / 断言数」。
   ⇒ **派单时值得要求成员在交付摘要里带上「我改了哪些文件 + 关键断言数」**，
   这样任何静默还原都能被立刻发现（本事故正是「33 pass → 该断言 0 命中」暴露的）。
4. **归因顺序**：成员报「我的改动被还原」时，**Lead 应先自查自己是否执行过回退类命令**，
   再怀疑其他成员。本事故 Lead 的第一反应是怀疑 f1/f2 的写范围冲突，方向错了。

## 五、与之同源的另一类事故：把失败伪装成成功

同一批还暴露了一个**性质相同**的问题（不是派单，但同属"静默降级"）：

`release.yml` 里 **4 处 `continue-on-error: true`**（含 **job 级**）+ **`setup-node` 缺 `registry-url`**
⇒ **npm 发布实际失败（`ENEEDAUTH`），而 CI 显示全绿、npm 上根本没有这个包**（registry 实测 404）。

**规则**：**交付终点（发布、上传、挂 Release）失败必须让流水线变红。**
唯一允许的软降级是「**这次不发布**」这种**显式选择**，且**必须打印 notice/warning**，不能静默。

## 六、恢复能力：不要让自己无法报告阻塞

本次最坏的一环是**失去了报告能力**：磁盘满 ⇒ `run_code` 起不来 ⇒ **连 `update_goal` 都调不了**。

**规则**：**保留一条不依赖临时磁盘的通道**。具体做法：

- **不要等磁盘满才清理** —— 在长任务中途**主动查一次** `df -h /tmp`；
- **把"需要清理"当作阻塞项立刻上报**，不要连续几十轮重复同一失败尝试（本次重复了 480+ 次，纯浪费）。
