## 1. 未实施项（按优先级）

### 1.0 注册表缺「会话源」——只有会话、没有任务行的工作区不在册（**代价 M，风险中，已定位到具体一行**）

**这是 fix.2 实施中（F1 实测）发现的、文档 §6 未实施项 3 的真实样本。**

**现象**：本机 3 个已打开的工作区**不在注册表**里——`/home/sixiao/aicode/fix/ZCode-CE`、`/tmp/pr1/ws`、
`/home/sixiao/aicode/digital_ecosystemV2/`（实测 tasks 表精确与模糊查询均为 0 行）。

**根因（具体到行）**：`taskIndexRepo.listWorkspaceRegistryEntries`
（`packages/services/src/session/taskIndexRepo.ts:1745-1762`）**只合并了任务索引源**：

```ts
const live = enumerateTaskIndexWorkspaceEntries(database); // ← 只有任务源
repo.upsertMany(live);
```

而 `workspaceRegistryRepo.ts:13` 的注释明写两源合并的第二源是**会话库**、由调用方以
`extraEntries` 传入 —— **该参数从未被任何调用方传入**。

**后果**：只有会话、没有任务行的工作区**永远不进注册表** ⇒ 侧栏的「注册表唯一源」口径下它们会消失。

**fix.2 的临时兜底**：F1 的实现取「注册表为主序列 ∪ 注册表里没有的 tab 追加在后」，
因此这 3 行**仍可见**（真实机器 55 行 = 52 + 3）。这是**可见性兜底**，不是口径修正。

**彻底解法**：补上 `extraEntries` 会话源。**F2 已实测评估（2026-09-27），结论：收益小、成本在所有权而非性能，不建议在 fix.2 做。**

**两处前提复核（Lead 已确认）**：

1. **那 3 个目录不是本缺口的受害者**。它们**不在任何一个服务端数据源里**——tasks 表精确与模糊均 0 行；
   会话库 `~/.zcode/cli/db/db.sqlite` 的 `directory` 列精确 0 行
   （`ZCode-CE` 的模糊 21 条命中的是**子目录** `.../apps/zcode-cli/packages/cli`）。
   ⇒ 它们**只在客户端设置**里，补会话源**修不好**它们；可见性只能靠 F1 的 tab 追加兜住。
2. **缺口规模 = 10 个**（尾斜杠口径敏感）：
   逐字节比对得 38，归一化尾斜杠后得 **10**（28 个是「仅尾斜杠不同」，如会话库 `.../test/test6`
   vs 注册表 `.../test/test6/`）。
   ⚠️ **注意口径适用范围**：「仅尾斜杠不同 = 0」**只对「本机 tab vs 注册表」成立**
   （两侧恰好同口径），**对「会话库 vs 注册表」不成立**。任何跨源比对都必须显式选定归一化口径。

**F2 的实测数据**：

| 维度     | 实测值                                                                                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 收益     | 会话库 distinct directory 67 个，其中 **10 个不在注册表**（全部为会话库独有；含 `/tmp/skill-gate-*` 测试残留、历史分析目录）                                                                                   |
| 性能成本 | `SELECT directory, COUNT(*), MAX(time_updated) GROUP BY directory` 实测 **4 ms**、返回 67 行 ⇒ **不存在「启动期全量读 262 MB」的问题**（是索引扫描 + 279 行的聚合）                                            |
| 真正成本 | **所有权与并发**：db.sqlite 的写者是 CLI agent 进程（`apps/zcode-cli/packages/adapters` 的 session-store），tasks-index 是另一个库。让服务端为只读再开一个 CLI 会话库句柄 = **新增第二条对同一文件的访问路径** |

**开工前必须先定的两个边界**（F2 指出）：

1. 谁持有 CLI 会话库句柄？其关闭职责、CLI 未初始化时文件不存在、远程 workspace 的库在哪一端。
2. 远程 workspace 的会话库归属哪一端。

**若将来要做，最小形态**（F2 建议，未验证）：不动 services 所有权，改由**已有会话列表接口**提供目录集合
（而非新开 sqlite 句柄），且只在注册表为空的**一次性回填**里使用。
**前置未验证**：该接口在服务端启动早期是否可用 —— 不得在未验证前承诺。

### 1.1 `workspaceTabs` 作用域模型迁移（**代价 L，风险中**）

**问题**：`workspaceTabs` 不只是侧栏的显示选择，它是**整个 UI 的工作区作用域来源**——
`useWorkspaceTaskLists`、`useGlobalTaskList`、`useGroupedTaskView`、`useLocalWorkspaceScopes`、
四个 Tasks section、`CommandCenterDialog` 等**共 239 处引用、12+ 个文件**都依赖它。

fix.2 只改了**侧栏与 task scope 的来源**，这些消费方仍以 tab 为口径。后果是：
某些视图（分组视图、命令面板、pinned/timeline/archived section）**仍按本机 tab 过滤**，
与侧栏的「注册表全集」口径**不一致**。

**要做**：把这些消费方的 scope 来源逐步迁到注册表，`tab` 只保留「激活态 + 远端身份」。

**为什么不在 fix.2 做**：239 处引用跨 12 文件，需要独立设计与充分回归，属架构改动。

### 1.2 远端工作区的多端可见性（**代价 M，风险中**）

**现状**：注册表**只有本地条目**（实测 `workspace_identity` 全为空）；
远端工作区（SSH/WSL/Docker）的**连接凭据只在本机**，因此**远端工作区无法三端一致**。

**这是技术必然，不是缺陷**——除非把远端凭据也托管到服务端（安全边界变更）。

**若要做**，需要先回答：凭据以什么形式、由谁持有、多端如何授权。**属安全设计，需独立 spec。**

### 1.3 「曾打开过」的持久标记（**代价 S，风险低**）

**现状**：fix.2 之后侧栏**不做任何「本机/其他」分组**，因此**不存在身份跃迁问题**。
但若将来要恢复某种「我用过的」排序或标记，需要一个**稳定判据**——
当前的 `!tabKeys.has()` 是**易变状态**（输入文字即跃迁），**不可用**。

**要做**：若需要该能力，用**持久标记**（如注册表加 `opened_by_client` 或本地记录），
而**不是**用「当前有没有 tab」。**这一点必须写进任何后续设计的前提。**

### 1.4 注册表默认视图的收敛口径（**代价 S，风险低**）

**现状**：默认视图 = 30 天活动 ∪ 置顶（本机实测 23/52 条），其余走「显示全部」。
用户反馈过「一堆」，fix.2 用折叠缓解，但**阈值是否合适未定**。

**要做**：结合真实使用决定是否收紧（如「只显示有未归档会话的」）。
F2 交付时会给出建议与理由，由决策者定。

### 1.5 注册表与「会话内容」的边界（**代价 S，风险低**）

**约定（须保持）**：注册表**只存元数据**（key / 路径 / firstSeen / lastActivity / 会话计数 / sources），
**不得**成为会话内容的第二份存储。理由是它由 `tasks` 表派生，重复存储会引入一致性窗口。

**若将来有人想在注册表里加「会话标题」等派生内容**：先回到本文与
`workspace-registry.md` §2.3（枚举只有一处）重新论证。

## 2. 已论证的技术事实（后续设计可直接依赖，勿重复验证）

| 事实                                       | 证据                                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| **列会话不需要 runtime**                   | `listTasks` → `taskIndexRepo.listTaskMetas`（`zcodeTaskServiceAdapter.ts:2308`）；数据在 SQLite      |
| **全量查询比逐条更快**                     | 实测：全量 0.64ms/49 行 vs 逐 workspace 52 次 1.04ms                                                 |
| **`listTaskMetas` 支持不传 workspacePath** | `taskIndexRepo.ts:1683` 注释明写                                                                     |
| **分组形状已就绪**                         | `useWorkspaceTaskLists` 已返回 `Map<workspaceKey, GroupResult>`                                      |
| **去重键无尾斜杠误判**                     | 实测 `buildTaskWorkspaceKey` 口径下「仅尾斜杠不同」= 0 条                                            |
| **注册表是派生数据**                       | `enumerateTaskIndexWorkspaceEntries` = 对 `tasks` 表 `GROUP BY workspace_key`                        |
| **上游侧栏无注册表概念**                   | 上游 `WorkspaceSidebar.tsx:362` 只用 `useTabStore(state => state.tabs)`；grep 注册表/未启动 = 0 命中 |

## 3. 决策记录（**有意不做**，防后人误以为漏了）

| 项                                | 原因                                                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 把「本机/其他工作区」做成**分组** | 分组判据只能是「本机有没有 tab」，那是**易变状态** ⇒ 输入文字即跃迁（用户指出）。改为**不分组 + 统一列表**，从根本上消除该问题 |
| 恢复「未启动」徽标                | 该状态对用户无意义（列会话不需要 runtime），且**按行渲染**会污染所有行；运行中状态已由官方既有圆圈表达                         |
| 让远端工作区三端一致              | 凭据是本地事实，托管到服务端属安全边界变更（见 1.2）                                                                           |
| 注册表改用单文件/多文件           | 枚举是派生数据，分文件会引入「任务已写、注册表未写」的窗口；SQLite 提供事务级保证，且迁移机制已就位                            |
